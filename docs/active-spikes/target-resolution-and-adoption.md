# Target resolution and adoption
Project Workflows needs to work both as a globally available set of procedures and as a versioned collection adopted by a Git project. The source checkout, target workspace, Git boundary, and document owner are separate facts. Confusing them can put a target project's notes in the global installation's parent.

## Scope
Resolve the target first; use global procedures directly for non-Git folders and explicitly global-only Git projects; preserve branch-per-project adoption for projects choosing pins. Let this collection maintain its own work in an ordinary `docs/` directory, using its root skills without recursive adoption. Improve the update procedure from a bounded copied-skill pilot, preserving local rules, supporting resources, existing notes, and repository boundaries.

Synced-drive projects require inspection of their established external Git-metadata arrangement before setup. This shared record documents the reusable preflight and recovery requirements; authorized consumer adoptions maintain their own private records and policy decisions. It does not create remote storage. A private consumer's details do not belong in shared guidance or this record.

## Reconciliation
Existing copies have no assumed ancestry with this collection. Compare complete folders, distinguish intentional project rules from outdated shared behavior, map retired entrypoints, and repair maintained navigation before removing redundant copies. Preserve unrelated product/service skills. Existing idea/pin lists remain content; a skill cutover is not permission to delete or split them.

## Verification and limits
Check all skill frontmatter/resources, neutral configuration, resolved target/document locations, relative links, and scoped diffs. Exercise global invocation for an external Git project and a plain folder, collection maintenance, and an adopted project's override. A local pilot must check its child ancestry, configuration, parent gitlink, preserved resources and notes, and repeated-adoption behavior. Publishing shared and project branches, then verifying remotely retrievable pins, is a separate step; a local clone cannot establish collaborator availability.

## Rollout follow-up
The authorized rollout exposed three procedure details worth making explicit: recoverable list migration only after separate content authorization; isolating a workflow pin from uncommitted parent scaffolding; and proving private bundle restoration without treating a public source URL as storage for a private adaptation. Shared guidance now covers those cases without importing any private project values or changing the neutral defaults.


## Global-only configuration and local authority
Targets may explicitly choose installed global skills plus parent-owned policy/config instead of a local collection. Every entrypoint checks declared local policy/adapters first. Config paths resolve from the selected config file, preserving `..` for pinned adoptions and supporting `.` at a target root. No target is inferred from the global installation. The update procedure now distinguishes authorized mode retirement from ordinary updates and handles dedicated recovery disposal only when explicitly requested. No consumer's private values or history are imported here.
