# Update Project Workflows
Resolve the actual requested target using [target resolution](../README.md#resolve-the-target) before selecting configuration or document paths. Global invocation does not target the installation checkout. Plain folders use global skills without adding a local collection or initializing Git.
## Authority and scope
Use the current project's instructions and adopted workflow source before a globally installed seed. An update request alone does not authorize publication, unknown changes, private-policy changes, or history rewriting. Honor explicit publication authorization already covering the requested repositories and refs; do not infer broader publication from it. Resolve material behavioral conflicts with the user while continuing independent authorized work.

This procedure handles the project collection's Git ancestry, configuration, templates, and parent pin. It does not require general skills or service integrations. Ordinary Git and document access suffice; a remote read requires an available authorized route.

## Bound the adoption inventory
For a multi-project request, first record a small inventory of the authorized roots: actual project/workspace and Git boundaries, source type (global-only, copied skills, or adopted collection), branch/pin, dirty or staged work, local routing, intentional conventions, and publication scope. Search for known workflow markers within those roots; do not turn discovery into a whole-disk or private-content audit. Do not treat reference copies, product submodules, or ordinary subject folders as new adoptions merely because they exist.

Plain folders use globally available workflows; do not create repositories or local collections for them. For Git projects, preserve their own adaptations even before divergence. Identify partial setup explicitly: staged `.gitmodules`/gitlinks and dirty child configuration are not a completed adoption. Reconcile that work without resetting, restaging unrelated files, or claiming the index entry is already committed. Check synchronized-storage constraints through [setup](../setup-project-workflows/SKILL.md#synchronized-storage).

Pilot a representative project before broad rollout. Use the existing spike/index to record the bounded comparison, retained differences, deliberate replacements, verification and remaining publication steps; no separate inventory framework is required.

## Establish the comparison
1. Map the repositories, their roles, and authorized consumers before editing: the shared collection, each project adaptation, and every parent that records their gitlinks. Inspect their status, index, remotes, actual branches, pins, and outgoing commits. A containing repository's `main` or `master` is not its workflow submodule's project branch. Preserve unrelated work; do not stash, reset, force checkout, or hide dirty state to proceed.
2. Read `workflow.toml` as project metadata, resolving its root relative to the adopted collection. Actual Git state establishes the branch and pin; stale configuration is not proof. No workflow env file is required. Preserve existing project-declared private-context mechanisms; inspect only explicitly relevant authorized context and keep private values out of output/commits.
3. Identify an explicitly designated canonical maintenance/global installation separately from ordinary adoptions. It uses shared `main` and neutral configuration; other projects still get adaptation branches even before divergence. If detached, select the intended branch only after checking its relationship to the recorded pin; a mismatched tip needs reconciliation, not a reset. For an ordinary adoption without a project branch, preserve the correct adopted history when creating one. Do not create an adaptation just to label the canonical installation. Follow user/local platform-neutral names, defaulting to `project/<project-slug>`. Branch changes belong to the workflow repository, not automatically to its parent or folder.
4. Retrieve the selected shared revision through the configured source. Identify the shared ancestor using Git, then compare ancestor → upstream and ancestor → project across complete folders, configuration, templates, and metadata. If history is shallow or ancestry unavailable, obtain appropriate history through an authorized read or label the comparison incomplete; do not use an arbitrary merge base.

## Classify and upstream reusable changes
Separate the comparison into shared improvements, project-only choices, and conflicts. Shared improvements can include procedures, templates, and general documentation. Project names, document-location choices, adoption metadata, private context, and project-specific procedures remain on the appropriate adaptation branch unless deliberately generalized. A public-safe project value is still not a neutral default for shared `main`.

Prepare reusable changes on a clean checkout or integration branch based on the actual shared target, normally `main`. Do not merge a project adaptation wholesale into shared `main`. A selected commit can be replayed only after its full diff is checked for project-only material; for a mixed commit, reconstruct the reviewed reusable change as a new scoped commit on the clean baseline. Keep project configuration and private narrative out of the upstream commit and its history. Inspect the complete outgoing range, not just the latest diff.

Validate the shared candidate with the collection's applicable authoring checks, links/resources, portability, and neutral configuration. Keep upstream contribution separate from downstream adoption so a maintainer can review the general change without project-only values. With explicit publication authority, use normal permitted integration to the shared target. If branch protection or access blocks it, preserve the candidate and use a draft pull request when that route is authorized; report the remaining merge blocker. Do not bypass protection or claim that a published proposal is already in `main`.

## Rename an existing project branch when requested
Verify the old branch, target name, ancestry, remote refs, and consumers. If the target name already exists, establish its ownership and relationship before selecting it; never overwrite it. A local branch rename preserves commit history and does not rename a remote branch.

Update the branch name in tracked `workflow.toml`, the parent's `.gitmodules` branch setting when present, current routing/docs, and any relevant local `submodule.<name>.branch` override. Check the renamed branch's Git upstream: a local rename can leave it tracking the old remote ref. Once the intended new remote branch exists, set and verify its upstream explicitly; do not push implicitly to the old name. Preserve old remote branches unless their deletion is separately authorized. Leave folder paths and the parent repository's branch unchanged unless a distinct change is needed and authorized. Preserve historical records of the old name as history rather than rewriting them as though the rename had always existed.

## Canonical installation and branch retirement
For a user-requested move from an adaptation to the canonical shared checkout, compare complete trees and ancestry first. Metadata-only differences do not mean the branch has no unique commits. Preserve any real procedure/configuration differences for an explicit decision; do not silently discard them or merge project-only metadata into shared `main`. Verify the actual shared revision, clean selected checkout, all known worktrees using the branch, and consumers before switching. Never disturb another agent's dirty work.

Before authorized retirement, create and verify a named recovery ref at the old tip; use a retrievable remote archive tag when remote history preservation is in scope. Move only authorized clean worktrees to their intended branch or detached revision. Delete only the exact approved local branch with normal safe deletion, and the exact remote branch only with explicit deletion authority. A recovery tag alone does not satisfy `git branch -d`'s mergedness check. Inspect the branch's actual upstream relationship; where safe deletion relies on the verified retained remote tip, retire local uses before deleting that remote ref. If Git refuses safe deletion or a worktree is still in use, retain the recovery and branch refs, report retirement incomplete, and do not force it. Verify recovery and branch absence. Update the canonical consumer's pin, branch metadata, and current routing without changing the containing repository's branch. Other consumers retain their adaptation branches and pins unless their migration is separately authorized.

## Reconcile each adaptation and its consumers
After the shared change is integrated, retrieve the exact accepted revision and compare it with every authorized adaptation's merge base. Merge shared `main` into each project branch using a history-preserving integration; for a pure fast-forward, a fast-forward is sufficient. Review the inputs before an automatic merge commit, and inspect the result. Git records merge commits from the merge operation; do not try to make a pathspec partial commit while a merge is in progress. Resolve semantic conflicts and preserve project-only `workflow.toml` values, procedure differences, and complete supporting files. Do not reset the project branch to upstream or replace the collection from a global copy.

Verify that the accepted shared revision is an ancestor of each resulting adaptation and that its remaining differences from shared `main` are intentional. Commit any branch-name/configuration repair with its own clear scope. When upstream integration is still pending, describe downstream work as prepared against that candidate rather than fully reconciled with accepted `main`.

Update each authorized parent's exact gitlink together with the directly affected routing and documents. For nested consumers, work from the deepest child outward: workflow adaptation, consuming repository, then any containing repository that pins the consumer. A branch setting does not advance a gitlink. Check child HEAD, the index entry, and the committed tree entry at each boundary; report any containing pin intentionally left for a separate task.

## Collection layout changes
When moving skill directories, carry each complete folder and inspect supporting assets, client metadata, relative links, templates, installed links, installer scripts, current routing, and compatibility wrappers. Update the authorized consumer and its live links together; do not leave global discovery pointing at removed paths or run an entire system installer to change a small selected set of links. Preserve user-owned real files and unrelated link targets. Validate syntax and idempotent link behavior in an isolated fixture. Historical documents may retain old paths as history, but maintained navigation must resolve.

A published layout change does not migrate every pinned consumer. Name consumers intentionally left at their old revision and leave their files, project configuration, and nested pins untouched. Their later adoption must update both the pin and routing.

## Upstream contributions and publishing
An upstream remote or local branch does not make a commit accessible to collaborators. Inspect remote ownership/access and the full set of commits each proposed push would introduce, including earlier unpublished work. If a parent is ahead by unrelated or private commits, do not publish them merely to deliver a new pin; leave the local pin update and explain that specific publication dependency. Any alternative integration must preserve the necessary history and remain within the authorized scope.

Where publication is authorized, push only the selected refs without force. Ordinary publication does not authorize branch deletion; separately authorized retirement follows the recovery checks above. Publish shared integration and the required adaptation commits before consumers that pin them, then proceed outward through the dependency graph. Verify exact remote refs after each step and ensure every committed gitlink is retrievable from its recorded URL. A rejected or uncertain operation needs inspection before any retry; do not change credentials, protections, or visibility to make it pass. Respect applicable repository restrictions and explicit user instructions.

Use a fresh recursive clone when feasible to verify the final published consumer and its nested pins. If the outermost consumer cannot be published safely, verify the independently published nested consumer and distinguish that evidence from a local outer-pin check. Cached refs, local-path clone overrides, frontmatter checks, and a successful fetch of shared `main` do not prove fresh collaborator access to all pinned commits. Record the exact verification limit instead of calling the whole chain complete.

## Existing copied skills
If there is no adopted submodule, compare the existing complete local folders with the designated seed before using setup-project-workflows to migrate. Preserve intentional divergence and supporting assets. No shared Git ancestor means a manual comparison, not a fake merge history. Do not erase existing copies until the replacement routes and behavior are verified. A rename alone does not authorize resetting local guidance.

Map each retiring entrypoint to its replacement before deleting copies. For the earlier collection, `setup-project-docs` maps to `setup-project-workflows`, `update-local-skills` maps to `update-project-workflows` for this collection, and `pin-issue`/`log-future-idea` map to `capture-for-later`. Also inspect legacy `setup-local-skills`: retire it when collection adoption supersedes its actual use, after checking callers and support files. If general or product-specific copying guidance is still useful, retain the minimal rules with that project or capability owner rather than keeping a redundant installer skill. General or service skills outside this collection retain their own ownership and update process. Reconcile support files such as client metadata and ignore templates at the corresponding destination; rename stale labels rather than carrying conflicting old behavior forward.

Distinguish intentional project rules from stale seed behavior. A shared correction is not a customization to preserve merely because a copied file predates it. Compare local authority, closure/commit rules, privacy, indexes, and cross-skill dependencies. References to project-owned skills outside the collection must still resolve after moving. Update current routing, installer/client links when in scope, and maintained navigation before retiring old copies. Leave historical references as history, and preserve existing scratch notes, registers, and logs unless their content migration is separately requested. Verify that a second setup/update would recognize the existing adoption rather than duplicate it.

## Completion
Validate changed skill frontmatter and supporting resources, TOML parsing, ignores, current links/routing, branch ancestry, project customization, and all changed pins. Use meaningful checks for the change, not tests that merely mirror prose. For requested workflow improvements, assess the previous coverage against the actual process and explain what changed beyond naming. Record failed checks and their bounded follow-up rather than silently replacing them with a broader success claim.

Report repository boundaries, old/new branch names, shared and adaptation commits, retained project differences, each consumer pin, publication evidence, and remaining blockers. Use the project's normal spike/index records for rationale; do not add duplicate version hashes to every skill. Leave unrelated files untouched and distinguish local readiness, shared-main integration, remote ref availability, recursive clone success, and client behavior.
